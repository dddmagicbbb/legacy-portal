# 01. 구조 파악 - 패키지 구성과 서비스 책임

> **이 문서는 무엇인가** - 리팩토링을 시작하기 전에 레거시 코드의 "지도"를 그리는 진단 문서다. 패키지·클래스가 어떻게 나뉘어 있고, 각 서비스가 무슨 책임을 지고 있는지를 사실 그대로 정리한다.
> **왜 보는가** - 구조를 모르고 고치면 어디까지가 외부 계약(API·DB값·동작)이고 어디가 내부 구현인지 구분할 수 없다. 책임이 어디에 몰려 있는지(God Class)와 무엇이 중복되는지를 먼저 확인해야 특성화 테스트의 범위와 리팩토링 우선순위를 정할 수 있다.

---

## 1. 기술 스택 / 실행 환경

| 항목 | 내용 |
|---|---|
| 언어·프레임워크 | Java 21 · Spring Boot 3.2 · Spring Data JPA · JUnit 5 |
| DB | MariaDB(localhost:3306)가 응답하면 사용, 아니면 H2 인메모리로 자동 전환 (`DataSourceConfig`) |
| 화면 | `static/index.html` 한 장 - Tailwind + 순수 JS SPA (사용자 선택형 데모 로그인) |
| 초기 데이터 | `DataSeeder` - 1 김사원(사원) · 2 박팀장(팀장) · 3 이임원(임원) · 4 최사원(사원) |
| 테스트 | **0개** (`src/test` 에는 `application.properties` 만 존재) |

## 3. 외부 계약 (보존 대상)

리팩토링 중 **절대 바꾸면 안 되는** 겉보기 계약이다.

### 3-1. REST API

| 메서드 | URL | 요청 | 응답 | 처리 |
|---|---|---|---|---|
| POST | `/api/approvals` | `Map` - title, content, type, priority, drafterId, approverId, amount(기본 0), urgent(기본 false) | `Approval` 엔티티 그대로 | `ApprovalService.create` |
| POST | `/api/approvals/{id}/process` | `Map` - userId, action(1/2/3/9), reason(기본 "") | 없음(void, 200) | `ApprovalService.processApproval` |
| GET | `/api/approvals/drafts/{userId}` | - | `List<Approval>` | 내가 기안한 결재 |
| GET | `/api/approvals/inbox/{userId}` | - | `List<Approval>` | 내가 결재자인 결재 |
| GET | `/api/users` | - | `List<User>` | 전체 사용자 |

### 3-2. DB 저장 코드값 (모두 `int`)

| 엔티티 | 필드 | 값 |
|---|---|---|
| Approval | status | 0 임시저장 · 1 상신 · 2 승인 · 3 반려 · 9 취소 |
| Approval | type | 1 지출 · 2 휴가 · 3 구매 · 4 기타 |
| Approval | priority | 1 낮음 · 2 보통 · 3 높음 |
| Notice | status | 0 임시 · 1 게시 · 9 내림 |
| Notice | category | 1 일반 · 2 긴급 · 3 인사 |
| Schedule | status | 0 예정 · 1 확정 · 9 취소 |
| User | role | 1 사원 · 2 팀장 · 3 임원 |

## 4. 서비스별 책임

### 4-1. ApprovalService (결재) - God Class

| public 메서드 | 책임 |
|---|---|
| `create(title, content, type, priority, drafterId, approverId, amount, urgent)` | 결재 생성. status=0, `urgent`면 priority=3 강제. 감사 로그 기록 |
| `processApproval(id, userId, action, reason)` | action 코드로 상신/승인/반려/취소 분기 - 아래 상태 전이 표 |
| `statusLabel(approval)` | status → 화면 라벨 문자열 ("임시저장"… / 그 외 "알수없음") |
| `amountGrade(approval)` | 금액 등급: 1000만↑ S · 100만↑ A · 10만↑ B · 그 외 C |
| `myDrafts(userId)` / `myInbox(userId)` | 기안자 / 결재자 기준 목록 조회 |

**상태 전이 (`processApproval`)**

| action | 허용 조건 | 결과 | 부수 효과 |
|---|---|---|---|
| 1 상신 | status=0 | status=1 | 지출(type 1) & 100만원↑ 이면 priority=3 · 결재자에게 메일 · 감사 로그 |
| 2 승인 | status=1 & 요청자=결재자 & role≥2 | status=2 | 기안자에게 메일 · 감사 로그 |
| 3 반려 | status=1 & 요청자=결재자 & role≥2 | status=3, rejectReason 저장 | 기안자에게 메일(사유 포함) · 감사 로그 |
| 9 취소 | status∈{0,1} & 요청자=기안자 | status=9 | 감사 로그 (메일 없음) |

- 결재·사용자가 없거나 조건 불충족이면 **예외 없이 조용히 return** (아무 변화 없음) - 레거시 동작이므로 보존 대상.
- 한 클래스가 **검증 · 상태 전이 · 영속화 · 메일 본문 생성 · 감사 로그 · 권한 판정 · 화면 라벨 · 금액 등급**까지 모두 떠안고 있다.

### 4-2. NoticeService (공지)

| public 메서드 | 책임 |
|---|---|
| `create(title, content, category, writerId, pinned)` | 공지 생성(status=0) · 감사 로그 |
| `publish(id, userId)` | role≥2 & status=0 이면 status=1(게시). 긴급(category 2)이면 **전 직원에게 메일** · 감사 로그. 조건 불충족 시 조용히 무시 |
| `statusLabel(notice)` | status → "임시"/"게시"/"내림"/"알수없음" |

### 4-3. ScheduleService (일정)

| public 메서드 | 책임 |
|---|---|
| `create(title, ownerId, startAt, endAt, location)` | 검증(제목 빈값·시간 null·종료<시작) → 같은 소유자의 취소(9) 아닌 일정과 **시간 겹침 검사** → 저장(status=0) · 감사 로그. 실패 시 원인 구분 없이 **`null` 반환** |
| `confirm(id, userId)` | 본인 일정 & status=0 이면 status=1(확정) · 감사 로그. 조건 불충족 시 조용히 무시 |

### 4-4. 그 외 구성 요소

| 클래스 | 책임 |
|---|---|
| `ApprovalController` | 요청 `Map`을 캐스팅해 서비스로 전달. DTO·검증 없음, 엔티티를 그대로 응답 |
| `UserController` | 리포지토리를 직접 호출해 사용자 목록 반환 (서비스 계층 없음) |
| `SmtpMailSender` | `send(to, subject, body)` - 콘솔 출력 |
| `FileAuditLogger` | `write(line)` - `[AUDIT]` 접두로 콘솔 출력 |
| 엔티티 4종 | 필드 + public getter/setter 만 존재 (행위 없음) |

## 5. 의존 관계

```
ApprovalController ──▶ ApprovalService ──▶ ApprovalRepository, UserRepository
                                       └─new─▶ SmtpMailSender, FileAuditLogger
NoticeService      ──▶ NoticeRepository, UserRepository
                   └─new─▶ SmtpMailSender, FileAuditLogger
ScheduleService    ──▶ ScheduleRepository, UserRepository
                   └─new─▶ FileAuditLogger
UserController     ──▶ UserRepository
```

- 리포지토리는 생성자 주입, **메일·감사 로거는 필드에서 직접 `new`** → 테스트에서 가짜로 교체할 수 없음.

## 6. 구조 진단 요약 (개선 대상 - 차후 리팩토링)

| 문제 | 위치 | 개선 방향 (CLAUDE.md) |
|---|---|---|
| God Class · Long Method (if 6단계 중첩) | `ApprovalService.processApproval` | 메서드 분리, 상신/승인/반려/취소로 내부 위임 (public 시그니처 유지) |
| 매직넘버 · 원시 타입 집착 | 전 엔티티·서비스 | 도메인 이름의 enum + `AttributeConverter` (DB 정수 유지) |
| 강결합 | 3개 서비스의 `new SmtpMailSender/FileAuditLogger` | 생성자 주입 (DIP) |
| 중복 코드 | 감사 로그 포맷·메일 본문·`statusLabel`·`role>=2` 판정 | 공통 모듈 추출 |
| 빈약한 도메인 · Feature Envy | 엔티티 setter + 서비스의 규칙 계산 | 상태 전이·금액 규칙을 엔티티로 이동 (Rich Domain) |
| DTO 부재 | `ApprovalController` (`Map` 입력, 엔티티 출력) | 요청/응답 record 분리 (JSON 구조 동일) |
| 나쁜 이름 | `d`, `u`, `s`, `proc`, `tmp`, `flag1`, `sc`, `n` | 의미 있는 완전한 이름 |
| 안전망 부재 | 테스트 0개 | **리팩토링 전에 특성화 테스트 먼저** |

> **보존 대상 vs 개선 대상** - 권한 없는 승인을 조용히 무시하는 것, 일정 생성 실패 시 `null` 반환 같은 결함도 **리팩토링 단계에서는 그대로 보존**한다. 이런 동작 변경은 리팩토링 완료 후 별도 재설계 단계에서 다룬다.
