# 02. 중복 코드 - 세 서비스(Approval·Notice·Schedule)에서 반복되는 로직

> **이 문서는 무엇인가** - `ApprovalService`·`NoticeService`·`ScheduleService` 에 복사·붙여넣기로 흩어진 같은(또는 거의 같은) 코드를 위치(파일:줄)와 함께 목록화한 진단 문서다.
> **왜 보는가** - 중복 코드(Duplicated Code)는 규칙 하나를 바꿀 때 여러 곳을 빠짐없이 고쳐야 하게 만들고, 한 곳만 고치면 동작이 서로 어긋나는 버그를 낳는다. 무엇이 "완전히 같은 중복"이고 무엇이 "미묘하게 다른 중복"인지 먼저 구분해 두어야, 공통 모듈로 추출할 때 레거시 동작(로그·메일 문구 포함)을 깨뜨리지 않는다.

> 줄 번호는 커밋 `b543df4` 기준이다.

## 2. 상세

### D1. 감사 로그 기록 (6곳) - 가장 많이 반복됨

같은 날짜 포맷 문자열 `"yyyy-MM-dd HH:mm:ss"` 와 `"[시각] 행위 id=… by=…"` 조립이 매번 새로 작성되어 있다.

| 위치 | 기록 문자열 |
|---|---|
| `ApprovalService.java:62-65` (create) | `[now] APPROVAL CREATE id=… by=… type=…` |
| `ApprovalService.java:164-165` (`writeAudit` - submit/approve/reject/cancel 공용) | `[now] {act} id=… by=…` |
| `NoticeService.java:44-45` (create) | `[now] NOTICE CREATE id=… by=…` |
| `NoticeService.java:69-70` (publish) | `[now] NOTICE PUBLISH id=… by=…` |
| `ScheduleService.java:62-63` (create) | `[now] SCHEDULE CREATE id=… by=…` |
| `ScheduleService.java:76-77` (confirm) | `[now] SCHEDULE CONFIRM id=… by=…` |

```java
// 6곳 모두 이 두 줄의 변형
String now = LocalDateTime.now().format(DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss"));
audit.write("[" + now + "] NOTICE PUBLISH id=" + n.getId() + " by=" + userId);
```

- **불완전한 추출:** `ApprovalService` 에는 이미 `writeAudit()` 가 있지만 같은 클래스의 `create()` 조차 이를 쓰지 않는다.
- **⚠ 미묘한 차이 (보존 대상):** `APPROVAL CREATE` 로그만 끝에 ` type=…` 이 붙는다. 공통 메서드로 합칠 때 이 꼬리를 잃으면 안 된다.

### D2. 메일 본문 조립 + 발송 (4곳)

`"안녕하세요 " + 이름 + "님,\n" + 안내문 + "\n제목: " + 제목` 구조와 `"[태그] " + 제목` 형태의 메일 제목이 반복된다.

| 위치 | 수신자 | 메일 제목 | 본문 안내문 | 추가 줄 |
|---|---|---|---|---|
| `ApprovalService.java:101-107` (상신) | 결재자 | `[결재요청] 제목` | 결재 요청이 도착했습니다. | `기안자ID: …` |
| `ApprovalService.java:119-124` (승인) | 기안자 | `[결재승인] 제목` | 결재가 승인되었습니다. | - |
| `ApprovalService.java:138-144` (반려) | 기안자 | `[결재반려] 제목` | 결재가 반려되었습니다. | `사유: …` |
| `NoticeService.java:63-67` (긴급 게시) | 전 직원 | `[긴급공지] 제목` | 긴급 공지가 게시되었습니다. | - |

- Approval 3곳은 **수신자 조회(`userRepo.findById(...).orElse(null)`) → null 이면 발송 생략** 까지 똑같이 반복된다.
- **⚠ 미묘한 차이 (보존 대상):** 상신은 `기안자ID`, 반려는 `사유` 줄이 추가로 붙는다. 템플릿화할 때 "추가 줄 목록"을 받을 수 있어야 한다.

### D3. 협력 객체 직접 생성 (5곳)

| 위치 | 코드 |
|---|---|
| `ApprovalService.java:37-38` | `new SmtpMailSender()`, `new FileAuditLogger()` |
| `NoticeService.java:24-25` | `new SmtpMailSender()`, `new FileAuditLogger()` |
| `ScheduleService.java:20` | `new FileAuditLogger()` |

- 같은 선언이 서비스마다 반복될 뿐 아니라, 인터페이스가 없어 테스트에서 가짜로 갈아끼울 수 없다 (DIP 위반).
- D1·D2 를 공통 모듈로 뽑을 때 **함께 생성자 주입으로 바꾸는 것이 자연스럽다.**

### D4. 조회 후 null 이면 조용히 종료 (3곳)

| 위치 | 대상 |
|---|---|
| `ApprovalService.java:76-84` (processApproval) | 결재 → 사용자 |
| `NoticeService.java:50-53` (publish) | 공지 → 사용자 |
| `ScheduleService.java:68-71` (confirm) | 일정 → 사용자 |

```java
Notice n = repo.findById(id).orElse(null);
if (n == null) return;
User u = userRepo.findById(userId).orElse(null);
if (u == null) return;
```

- **⚠ 보존 대상:** "없으면 예외 없이 아무 일도 안 함" 은 레거시 동작이다. 중복을 줄이더라도 예외로 바꾸면 안 된다 (`Optional` + `ifPresent` 등으로 형태만 정리).
- `ScheduleService.confirm` 은 조회한 `u` 를 존재 확인 외에는 쓰지 않는다 - 그래도 "사용자가 없으면 무시" 동작은 유지해야 한다.

### D5. 권한 판정 `role >= 2` (3곳)

| 위치 | 의미 |
|---|---|
| `ApprovalService.java:114` | 승인 권한 (팀장 이상) |
| `ApprovalService.java:133` | 반려 권한 (팀장 이상) |
| `NoticeService.java:56` | 게시 권한 (팀장 이상) |

- 같은 규칙("팀장 이상")이 매직넘버로 세 번 등장한다. 기준이 바뀌면 세 곳을 동시에 고쳐야 한다.
- 개선 방향: 사용자 역할 enum(예: `UserRole`) + `User.isManagerOrAbove()` 같은 도메인 메서드로 한 곳에 모은다.

### D6. `statusLabel` - 숫자 → 라벨 if 사슬 (2곳)

| 위치 | 매핑 |
|---|---|
| `ApprovalService.java:169-179` | 0 임시저장 · 1 상신 · 2 승인 · 3 반려 · 9 취소 · 그 외 알수없음 |
| `NoticeService.java:76-82` | 0 임시 · 1 게시 · 9 내림 · 그 외 알수없음 |

- 값과 라벨은 다르지만 **구조(if 사슬 + "알수없음" 기본값)가 판박이**다.
- 개선 방향: 상태 enum 에 라벨을 필드로 두고, 알 수 없는 코드는 "알수없음" 을 돌려주는 기존 동작을 유지한다.

### D7. 승인·반려 분기 블록 (`ApprovalService` 내부 1쌍)

`ApprovalService.java:111-127` (승인) 과 `:130-147` (반려) 는 아래 골격이 **줄 단위로 거의 동일**하다.

```
if (상태 == 1 상신)
  if (요청자 == 결재자)
    if (role >= 2)
      상태 변경 → updatedAt → save → 기안자에게 메일 → 감사 로그
```

- 차이: 결과 상태(2 vs 3), 반려 시 `rejectReason` 저장, 메일 제목·안내문, 로그 행위명.
- 개선 방향: "결재자 처리 가능 여부" 가드를 메서드(또는 엔티티 행위)로 추출하고 차이점만 분기.

### D8. 당사자 일치 확인 (4곳)

| 위치 | 확인 |
|---|---|
| `ApprovalService.java:113`, `:132` | `d.getApproverId() != null && d.getApproverId().equals(userId)` |
| `ApprovalService.java:152` | `d.getDrafterId() != null && d.getDrafterId().equals(userId)` |
| `ScheduleService.java:72` | `sc.getOwnerId().equals(userId)` |

- **⚠ 미묘한 차이 (보존 대상):** Approval 은 null 검사를 하지만 Schedule 은 하지 않는다 (`ownerId` 가 null 이면 NPE). 합치더라도 이 차이가 동작에 영향을 주는지 특성화 테스트로 먼저 확인해야 한다.
- 개선 방향: `approval.isApprover(userId)`, `approval.isDrafter(userId)`, `schedule.isOwnedBy(userId)` 처럼 엔티티 행위로 이동 (Feature Envy 해소).

### D9. 상태 변경 + `updatedAt` 갱신 + 저장 (`ApprovalService` 4곳)

`ApprovalService.java:97-99`, `:115-117`, `:134-137`, `:153-155`

```java
d.setStatus(N);
d.setUpdatedAt(LocalDateTime.now());
repo.save(d);
```

- 상태를 바꿀 때마다 `updatedAt` 갱신을 호출자가 기억해야 한다.
- 개선 방향: `Approval` 에 `submit()/approve()/reject()/cancel()` 같은 상태 전이 메서드를 두고 내부에서 `updatedAt` 을 함께 갱신 (Rich Domain).

## 3. 추출 계획 (개선 대상 - 차후 리팩토링)

| 순서 | 대상 | 추출 결과(안) | 해소되는 중복 |
|---|---|---|---|
| 1 | 감사 로그 | 공통 `AuditRecorder`(가칭) - 시각 포맷·`id=… by=…` 조립 담당, 추가 꼬리(` type=…`) 지원 | D1 |
| 2 | 메일 | 공통 알림 컴포넌트 - 인사말·제목 태그·추가 줄 템플릿 | D2 |
| 3 | 의존성 | 위 두 컴포넌트를 각 서비스에 **생성자 주입** | D3 |
| 4 | 권한·당사자 | `UserRole` enum + `User`·`Approval`·`Schedule` 도메인 메서드 | D5, D8 |
| 5 | 상태 | 도메인별 상태 enum(라벨 포함, DB 정수는 `AttributeConverter`) | D6 |
| 6 | 상태 전이 | `Approval` 상태 전이 메서드 + 승인/반려 공통 가드 | D7, D9 |
| 7 | 조회 가드 | `Optional` 기반으로 형태 정리 (조용한 무시는 유지) | D4 |

> **전제:** 어떤 추출이든 **시작 전에 특성화 테스트로 현재 동작을 고정**한다. 특히 ⚠ 표시한 "미묘한 차이"(로그 꼬리, 메일 추가 줄, null 검사 유무, 조용한 무시)는 합치는 과정에서 사라지기 쉬우므로 테스트로 반드시 잡아 둔다.
