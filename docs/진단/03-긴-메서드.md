# 03. 긴 메서드 - 메서드 길이와 중첩 깊이 측정

> **이 문서는 무엇인가** - 프로덕션 코드의 모든 메서드(getter/setter 제외)를 길이(줄 수)와 제어문 중첩 깊이로 측정해, **50줄 초과** 또는 **중첩 3단계 이상**인 메서드를 찾아낸 진단 문서다.
> **왜 보는가** - 긴 메서드(Long Method)와 깊은 중첩(Arrow Code)은 한 메서드가 여러 책임을 지고 있다는 신호다. 읽기·테스트·변경이 모두 어려워지고 분기 누락 버그가 숨기 쉽다. 수치로 측정해 두면 "메서드 추출"·"가드 절" 리팩토링의 우선순위와 완료 기준(몇 줄·몇 단계까지 줄였는지)을 객관적으로 정할 수 있다.

> 측정 기준: 커밋 `ecf2dec`, `src/main/java` 전체.
> - **줄 수** = 시그니처 줄 ~ 닫는 `}` 까지 (주석·빈 줄 포함). 괄호 안은 주석·빈 줄을 뺀 코드 줄 수.
> - **중첩 깊이** = 메서드 본문 안에서 `if`·`for`·`try` 등 제어문이 겹친 최대 단계 (`else if` 는 같은 단계, 중괄호 없는 한 줄 `if` 도 1단계로 계산).
> - 기준선: **길이 50줄 초과 = 위험**, **중첩 3단계 이상 = 주의**, **4단계 이상 = 위험**.

## 3. 상세 분석

### 3-1. 🔴 `ApprovalService.processApproval` - 86줄 · 중첩 5단계

action 코드 하나로 4가지 업무를 한 메서드에서 처리한다.

| 구간 | 줄 | 내용 | 해당 구간 최대 중첩 |
|---|---|---|:---:|
| 조회 가드 | 76-84 | 결재·사용자 조회, 없으면 조용히 `return` | 1 |
| 지역변수 | 86-87 | `s`(상태), `proc`(action 복사본) | 0 |
| 상신 (`proc == 1`) | 90-109 | 상태 확인 → 금액 기준 우선순위 상향 → 저장 → 결재자 메일 → 로그 | 3 |
| 승인 (`proc == 2`) | 110-128 | 상태 → 결재자 일치 → 권한 → 저장 → 기안자 메일 → 로그 | **5** |
| 반려 (`proc == 3`) | 129-148 | 승인과 동일 골격 + 반려 사유 저장 | **5** |
| 취소 (`proc == 9`) | 149-159 | 상태 → 기안자 일치 → 저장 → 로그 | 3 |

**가장 깊은 경로 (승인·반려 분기, 5단계)**

```
processApproval
└─ 1 if (proc == 2)                         // 어떤 업무인가
   └─ 2 if (s == 1)                         // 상신 상태인가
      └─ 3 if (결재자 == 요청자)             // 당사자인가
         └─ 4 if (u.getRole() >= 2)          // 권한이 있는가
            └─ 5 if (drafter != null)        // 메일 수신자가 있는가
                  mail.send(...)
```

- **문제:** 진짜 하고 싶은 일(상태 변경·알림)이 4~5단계 안쪽에 묻혀 있다. 조건 4개가 모두 "아니면 아무것도 안 함"이라서 **가드 절(early return)** 로 평탄화하기 좋은 구조다.
- **책임 수:** 분기 선택 · 상태 전이 검증 · 권한 판정 · 도메인 규칙(금액 기준 우선순위) · 영속화 · 메일 본문 생성 · 감사 로그 → **7가지**.
- **개선 방향 (차후 리팩토링):**
  1. 분기별로 `submit` / `approve` / `reject` / `cancel` private 메서드 추출 - **public `processApproval(id, userId, action, reason)` 시그니처는 유지**하고 내부에서 위임만 한다.
  2. 각 메서드 안의 중첩 조건을 가드 절로 평탄화 → 목표 **중첩 1~2단계**.
  3. 상태 전이·당사자·권한 판정을 `Approval`·`User` 의 도메인 메서드로 이동 (Rich Domain).
  4. 메일·감사 로그는 공통 컴포넌트로 추출 (→ [02-중복-코드.md](02-중복-코드.md) D1·D2).

### 3-2. 🔴 `NoticeService.publish` - 25줄 · 중첩 4단계

```
publish
└─ 1 if (u.getRole() >= 2)                   // 권한
   └─ 2 if (n.getStatus() == 0)              // 임시 상태인가
      └─ 3 if (n.getCategory() == 2)         // 긴급 공지인가
         └─ 4 for (User member : 전 직원)     // 전 직원 메일
```

- 짧지만 **권한 → 상태 → 분류 → 반복**이 겹쳐 있다.
- **개선 방향:** 권한·상태 조건을 가드 절로, "긴급 공지 전 직원 메일"을 별도 메서드로 추출 → 목표 중첩 1~2단계.

### 3-3. 🟡 `ScheduleService.create` - 39줄 · 중첩 3단계

```
create
├─ 1 if (제목 빈값) return null              // 검증 3개 (이미 가드 절 형태)
├─ 1 if (시간 null) return null
├─ 1 if (종료 < 시작) return null
└─ 1 for (기존 일정)                          // 시간 겹침 검사
   └─ 2 if (status != 9)
      └─ 3 if (시간대 겹침) flag1 = true
```

- 검증부는 이미 가드 절이라 양호하다. 중첩은 **시간 겹침 검사 루프**에서만 생긴다.
- 한 메서드에 **검증 · 겹침 검사 · 생성 · 감사 로그** 4가지 책임이 들어 있다.
- **개선 방향:** 겹침 검사를 `hasOverlappingSchedule(ownerId, startAt, endAt)` 같은 메서드로, 겹침 조건식을 `Schedule.overlaps(startAt, endAt)` 도메인 메서드로 추출. `flag1` 은 `isOverlapping` 처럼 의미 있는 이름으로.

## 4. 리팩토링 우선순위와 목표 수치

| 순서 | 대상 | 현재 | 목표 | 주요 기법 |
|:---:|---|---|---|---|
| 1 | `ApprovalService.processApproval` | 86줄 · 중첩 5 | public 메서드 ~15줄(위임만) · 분기 메서드 각 20줄 이하 · 중첩 2 이하 | 메서드 추출, 가드 절, 도메인 이동 |
| 2 | `NoticeService.publish` | 25줄 · 중첩 4 | 중첩 2 이하 | 가드 절, 메서드 추출 |
| 3 | `ScheduleService.create` | 39줄 · 중첩 3 | 중첩 2 이하 · 25줄 이하 | 메서드 추출, 도메인 이동 |

> **보존 대상 (동작·계약):** 메서드를 쪼개도 public 시그니처, 조건 불충족 시 **조용히 무시**(void 메서드는 아무 일 없음, `ScheduleService.create` 는 `null` 반환), 상태 전이 결과·메일·로그 내용은 그대로 유지한다.
> **개선 대상 (구조):** 메서드 길이, 중첩 깊이, 책임 분리. 동작 변경(예외 도입 등)은 리팩토링 완료 후 별도 재설계 단계에서 다룬다.
> **전제:** 분리 전에 각 분기(상신·승인·반려·취소의 성공/무시 케이스)를 특성화 테스트로 먼저 고정한다.
