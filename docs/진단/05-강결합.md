# 05. 강결합 - 직접 `new` 로 생성하는 의존성

> **이 문서는 무엇인가** - 클래스가 협력 객체를 주입받지 않고 내부에서 `new` 로 직접 만들거나 정적 호출로 붙잡고 있는 곳을 모두 찾아, "고쳐야 할 강결합"과 "그대로 둬도 되는 생성"으로 분류한 진단 문서다.
> **왜 보는가** - `new SmtpMailSender()` 처럼 구체 클래스를 직접 만들면 그 클래스에 **컴파일 단계에서 묶여** 다른 구현으로 바꿀 수 없고, 테스트에서 가짜(Fake/Mock)로 갈아끼워 "메일이 보내졌는가"를 검증할 수도 없다. 상위 모듈이 구체 구현이 아닌 추상(인터페이스)에 의존하게 하는 **DIP(의존 역전 원칙)** 와 **생성자 주입**으로 바꾸기 전에, 어떤 의존성이 대상인지 범위를 확정해야 한다.

> 측정 기준: 커밋 `f55e294`, `src/main/java` 전체.

---

## 1. 결과 요약

| 분류 | 건수 | 판단 |
|---|:---:|---|
| 🔴 **A. 협력 객체 직접 `new`** (서비스 → 메일·감사 로거) | **5** | **리팩토링 대상** - 생성자 주입 + 인터페이스 |
| 🟡 **B. 숨은 정적 의존성** (`LocalDateTime.now()`) | 13 | 선택적 개선 - 시간 고정이 필요한 테스트가 생기면 `Clock` 주입 |
| 🟢 **C. 정상적인 생성** (엔티티·빌더·설정) | 9 | 유지 - 강결합 아님 |

- 리포지토리(`ApprovalRepository` 등)는 이미 **생성자 주입**이라 문제없다. 같은 클래스 안에서 "리포지토리는 주입, 메일·로거는 직접 `new`" 로 **방식이 섞여 있다**는 점이 핵심이다.
- `SmtpMailSender`·`FileAuditLogger` 는 `@Component` 가 아니고 인터페이스도 없다 → 지금 구조로는 스프링이 주입해 줄 방법 자체가 없다.

### 현재 의존 구조

```
ApprovalService ──(주입)──▶ ApprovalRepository, UserRepository
        └──(new)──▶ SmtpMailSender (구체)   ──▶ System.out
        └──(new)──▶ FileAuditLogger (구체)  ──▶ System.out

NoticeService   ──(주입)──▶ NoticeRepository, UserRepository
        └──(new)──▶ SmtpMailSender, FileAuditLogger

ScheduleService ──(주입)──▶ ScheduleRepository, UserRepository
        └──(new)──▶ FileAuditLogger
```

### 이 구조가 만드는 문제

| 문제 | 구체적인 영향 |
|---|---|
| **테스트에서 교체 불가** | 특성화 테스트가 "상신하면 결재자에게 `[결재요청] 제목` 메일이 간다"를 검증하려면 `System.out` 을 가로채는 수밖에 없다. 가짜 메일 발송기를 넣을 틈이 없다. |
| **구현 교체 시 호출부 전부 수정** | 실제 SMTP(`JavaMailSender`)나 DB 감사 테이블로 바꾸려면 서비스 3개를 모두 열어 고쳐야 한다 (OCP 위반). |
| **의존성이 생성자에 드러나지 않음** | 생성자만 보면 리포지토리 2개에만 의존하는 것처럼 보인다. 메일·로그라는 부수 효과가 숨어 있다. |
| **인스턴스 중복** | 같은 무상태 객체가 서비스마다 따로 생성된다 (메일 2개, 로거 3개). 기능상 문제는 없지만 스프링 빈 하나로 충분하다. |

## 3. 🟡 B. 숨은 정적 의존성 - `LocalDateTime.now()` (13곳)

| 파일 | 줄 | 용도 |
|---|---|---|
| `approval/ApprovalService.java` | 57, 58 | 생성 시 `createdAt`·`updatedAt` |
| 〃 | 98, 116, 136, 154 | 상신·승인·반려·취소 시 `updatedAt` |
| 〃 | 62, 164 | 감사 로그 시각 |
| `notice/NoticeService.java` | 40 | 생성 시 `createdAt` |
| 〃 | 44, 69 | 감사 로그 시각 |
| `schedule/ScheduleService.java` | 62, 76 | 감사 로그 시각 |

- `new` 는 아니지만 **시스템 시계에 정적으로 묶인** 의존성이다. 테스트에서 "updatedAt 이 정확히 언제인가"를 고정할 수 없다.
- **판단:** 특성화 테스트는 시각 값 자체보다 "갱신되었는가(null 아님 / 이전보다 이후)"를 검증하면 충분하므로 **우선순위 낮음**. 시각 고정이 꼭 필요해지면 `java.time.Clock` 을 빈으로 주입해 `LocalDateTime.now(clock)` 으로 바꾼다.
- 감사 로그 시각 계산(62·164·44·69·62·76)은 A 의 감사 로거를 추출할 때 **그 안으로 옮기면** 서비스에서 자연히 사라진다 (→ [02-중복-코드.md](02-중복-코드.md) D1).

## 4. 🟢 C. 정상적인 생성 (유지)

| 위치 | 코드 | 유지 이유 |
|---|---|---|
| `approval/ApprovalService.java:48` | `new Approval()` | 엔티티 생성 - 서비스의 본래 책임. 교체할 "다른 구현"이 없다 |
| `notice/NoticeService.java:33` | `new Notice()` | 〃 |
| `schedule/ScheduleService.java:52` | `new Schedule()` | 〃 |
| `DataSeeder.java:24-27` | `new User(...)` × 4 | 초기 데이터 엔티티 생성 |
| `DataSourceConfig.java:31`, `:40` | `DataSourceBuilder.create()` | `@Configuration` 의 `@Bean` 팩토리 - **객체를 만들어 스프링에 넘기는 곳**이 바로 여기다 |
| `DataSourceConfig.java:51-53` | `DriverManager.setLoginTimeout/getConnection` | 기동 시 1회 접속 확인용 정적 JDBC API - 설정 클래스 내부 사용이라 허용 |

> 판단 기준: **값·엔티티(데이터)** 와 **스프링 설정 클래스 안의 생성**은 `new` 해도 강결합이 아니다. 문제는 **행위를 가진 협력 객체(서비스·외부 연동)** 를 사용하는 쪽이 직접 만드는 경우다.
> 단, 엔티티 생성 후 setter 를 줄줄이 호출하는 방식(빈약한 도메인)은 별도 문제다 - 생성자/정적 팩토리로 옮기는 것은 Rich Domain 단계에서 다룬다.

### 참고 - 생성은 아니지만 결합이 강한 곳

| 위치 | 내용 | 비고 |
|---|---|---|
| `user/UserController.java` | 컨트롤러가 `UserRepository` 를 직접 주입받아 호출 (서비스 계층 생략) | 주입은 되어 있어 DIP 문제는 아님. 계층 건너뛰기 - 낮은 우선순위 |
| `common/SmtpMailSender.java:12-16`, `FileAuditLogger.java:11` | `System.out.println` 으로 출력 | 실습용 구현 세부사항. 인터페이스 뒤로 숨기면 서비스와는 무관해진다 |

## 5. 리팩토링 방향 (개선 대상 - 차후)

### 목표 구조

```
ApprovalService ──(생성자 주입)──▶ MailSender «interface» ◀── SmtpMailSender  @Component
                └─(생성자 주입)──▶ AuditLogger «interface» ◀── FileAuditLogger @Component
NoticeService   ──(생성자 주입)──▶ MailSender, AuditLogger
ScheduleService ──(생성자 주입)──▶ AuditLogger
```

| 순서 | 작업 | 비고 |
|:---:|---|---|
| 1 | `MailSender`·`AuditLogger` 인터페이스 추출 (`common`) | 메서드 시그니처는 기존 `send(to, subject, body)`·`write(line)` 그대로 |
| 2 | `SmtpMailSender`·`FileAuditLogger` 가 인터페이스 구현 + `@Component` 등록 | 클래스 이름·출력 형식 유지 |
| 3 | 세 서비스의 필드 `new` 제거 → `final` 필드 + **생성자 주입** | A1~A5 해소 |
| 4 | 테스트에서 가짜 구현(`RecordingMailSender` 등)을 주입해 메일·로그 검증 | `System.out` 가로채기 불필요 |
| 5 | (선택) `Clock` 빈 주입 | B 해소 - 필요할 때만 |

### 반드시 지킬 것 (보존 대상)

- **출력 내용 동일:** 메일 수신자·제목·본문, 감사 로그 문자열(`[시각] 행위 id=… by=…`, 결재 생성의 ` type=…` 꼬리 포함)은 한 글자도 바뀌면 안 된다.
- **호출 시점·횟수 동일:** 어떤 조건에서 메일·로그가 나가고 안 나가는지(예: 취소는 메일 없음, 수신자가 없으면 메일 생략, 긴급 공지는 전 직원 수만큼 발송)를 그대로 유지한다.
- **public 계약 유지:** 서비스의 public 메서드 시그니처는 그대로. 바뀌는 것은 **생성자 파라미터뿐**이며, 스프링이 주입하므로 컨트롤러 등 호출부는 영향이 없다.
- **특성화 테스트:** 주입 방식으로 바꾼 뒤에도 기존 테스트 본문(호출·기대값)은 그대로 green 이어야 한다. 테스트에서 서비스를 직접 `new` 로 만든다면 생성자 인자가 늘어나는 부분만 **컴파일을 위한 기계적 수정**으로 허용되며, 그 diff 는 따로 확인받는다.
