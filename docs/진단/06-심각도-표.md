# 06. 심각도 표 - 진단 01~05 종합

> **이 문서는 무엇인가** - 진단 01~05 에서 찾은 코드 스멜을 한 표로 모아 **심각도(영향 × 범위)** 순으로 정렬한 종합 진단 문서다. 각 스멜이 어디에 있고, 어떤 기법으로 고치며, 리팩토링 단계에서 고쳐도 되는지(구조) 아니면 재설계 단계로 미뤄야 하는지(동작)를 함께 적었다.
> **왜 보는가** - 스멜을 다 찾았다고 한꺼번에 고칠 수는 없다. 피해가 크고 넓게 퍼진 것, 다른 리팩토링의 **전제 조건**이 되는 것부터 처리해야 적은 위험으로 가장 큰 효과를 얻는다. 심각도 표는 리팩토링 순서를 정하는 **우선순위 백로그**이자, 끝난 뒤 무엇이 개선되었는지 확인하는 기준선이다.

> 기준 커밋: `f55e294` · 개별 스멜 목록(체크리스트)은 [../smells.md](../smells.md) 참고.

## 1. 심각도 산정 기준

**점수 = 영향도(1~3) × 범위(1~3)** → 최대 9점

| 축 | 3점 | 2점 | 1점 |
|---|---|---|---|
| **영향도** - 방치하면 생기는 피해 | 버그·회귀를 직접 유발하거나 다른 리팩토링을 **막는다** | 변경 비용을 크게 늘린다 | 가독성만 떨어뜨린다 |
| **범위** - 퍼진 정도 | 3개 도메인 전체 또는 DB·API 계약에 걸침 | 2개 클래스 이상 / 여러 메서드 | 한 곳 |

| 등급 | 점수 | 의미 |
|---|:---:|---|
| 🔴 치명 | 9 | 지금 바로 - 이것부터 처리하지 않으면 나머지가 위험하다 |
| 🟠 높음 | 6 | 1차 리팩토링 범위 |
| 🟡 중간 | 3~4 | 상위 작업을 하면서 함께 정리 |
| 🟢 낮음 | 1~2 | 여유 있을 때 / 선택 |

## 3. 등급별 요약

### 🔴 치명 (9점) - 4건

| ID | 왜 치명인가 |
|---|---|
| S01 | 안전망이 없으면 **어떤 리팩토링도 동작 보존을 증명할 수 없다.** 모든 작업의 전제 조건 |
| S02 | 결재의 핵심 업무 4가지가 한 메서드에 엉켜 있어 **한 분기를 고치면 다른 분기가 깨질 위험**이 가장 크다 |
| S03 | 숫자의 의미가 코드에 없고 DB·API·화면에 퍼져 있다. 잘못 바꾸면 **저장 데이터가 깨진다**(9 → ordinal 4 등) |
| S04 | 메일·로그를 가짜로 바꿀 수 없어 **S01(테스트 작성)을 직접 방해**한다 |

### 🟠 높음 (6점) - 3건

| ID | 핵심 |
|---|---|
| S05 | 규칙 하나를 바꿀 때 최대 6곳을 함께 고쳐야 한다 - 일부만 고치면 로그·메일 형식이 어긋난다 |
| S06 | 규칙이 서비스에 흩어져 있어 S02·S05 를 고쳐도 다시 같은 모양으로 돌아간다 |
| S07 | 필드명 오타·타입 오류가 **실행 시점에야** 드러난다 (`ClassCastException`, NPE). 엔티티가 API 계약에 그대로 노출 |

### 🟡 중간 · 🟢 낮음 - 8건

S08~S11, S13~S16 은 대부분 **상위 작업을 하면서 함께 해소**된다.
- S08 깊은 중첩 → S02 방식(메서드 추출 + 가드 절)을 공지·일정에 동일 적용
- S09 나쁜 이름 · S13 주석 스멜 → 메서드를 추출하거나 enum 을 도입할 때 이름을 바로 개선
- S11 표현 로직 → S03 enum 에 라벨을 넣으면 해소
- S14·S15 → S05 감사 로그 공통화 시 날짜 포맷·시각 계산이 한 곳으로 모임

## 4. 권장 리팩토링 순서

```
① S01 특성화 테스트 작성          ← 모든 작업의 전제. 현재 동작(조용한 무시 포함)을 그대로 고정
        │
② S04 강결합 해소 (DIP·생성자 주입) ← 메일·로그를 가짜로 바꿔 테스트에서 검증 가능하게
        │
③ S03 매직넘버 → enum (+ AttributeConverter, DB 정수 유지)
        │
④ S02 processApproval 분해 (+ S08 공지·일정 중첩, S09 이름 개선)
        │
⑤ S05 중복 제거 (감사 로그·메일 공통 모듈) + S06 도메인으로 규칙 이동
        │
⑥ S07 요청/응답 DTO(record) 분리 (JSON 구조 동일)
        │
⑦ S10 · S11 · S13~S16 정리
        │
⑧ ── 리팩토링 완료 ── → S12 조용한 실패를 예외/결과 타입으로 바꾸는 "재설계" (별도 단계, 동작 변경)
```

> **②를 ③보다 먼저 두는 이유:** 메일·로그를 주입 가능하게 만들어야 ①의 특성화 테스트가 "상신하면 결재자에게 메일이 간다" 같은 부수 효과까지 고정할 수 있다. 다만 ②는 생성자만 바꾸는 작은 변경이므로, ①을 먼저 작성하되 메일·로그 검증은 `System.out` 캡처로 시작하고 ② 이후 가짜 구현으로 바꿔도 된다.

## 5. 리팩토링 전 과정에서 지킬 것 (보존 대상)

| 보존 대상 | 내용 |
|---|---|
| API | URL·HTTP 메서드 (`/api/approvals/{id}/process` 하나로 유지), 요청/응답 JSON 구조, 숫자 코드 그대로 |
| public 계약 | `processApproval(id, userId, action, reason)` 등 시그니처 유지 - 내부만 위임 |
| DB 값 | 0/1/2/3/9 등 기존 정수. `@Enumerated(STRING/ORDINAL)` 금지 |
| 동작 | 조용한 무시, `null` 반환, 메일·로그 문구와 발송 조건, 알 수 없는 코드의 처리 방식 |
| 특성화 테스트 | 한번 만든 테스트의 본문(호출·기대값)은 절대 수정 금지 - 정수 리터럴 그대로 |
