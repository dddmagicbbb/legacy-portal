# 07. 심각도 점수 - 영향도 × 수정난이도

> **이 문서는 무엇인가** - 스멜 16종(S01~S16, [../smells.md](../smells.md))을 **영향도(방치하면 얼마나 아픈가)** 와 **수정난이도(고치기가 얼마나 어렵고 위험한가)** 두 축으로 각각 1~5점 채점하고, 곱한 점수로 심각도 ★(1~5개)를 매긴 문서다.
> **왜 보는가** - [06-심각도-표.md](06-심각도-표.md) 가 "피해가 얼마나 넓게 퍼졌나(영향 × 범위)"로 **처리 순서**를 정했다면, 이 문서는 "고치는 데 드는 비용과 위험"을 더해 **작업 계획**을 세우기 위한 것이다. 영향이 크면서 고치기도 어려운 스멜은 기술 부채의 이자가 가장 비싸고, 특성화 테스트와 작은 단계 분할이 꼭 필요하다. 반대로 영향은 큰데 쉽게 고칠 수 있는 스멜은 먼저 처리해 효과를 얻는 **빠른 성과(Quick Win)** 다.

> 기준 커밋: `0fb388a`

---

## 1. 채점 기준

### 영향도 (1~5) - 방치하면 생기는 피해

| 점수 | 기준 |
|:---:|---|
| 5 | 버그·데이터 손상을 직접 유발하거나, **다른 리팩토링을 막는다** |
| 4 | 변경할 때마다 회귀 위험이 크다 / 외부 계약(API·DB)에 걸쳐 있다 |
| 3 | 변경 비용을 눈에 띄게 늘린다 (여러 곳 동시 수정) |
| 2 | 읽고 이해하는 데 시간을 잡아먹는다 |
| 1 | 미관 · 일관성 문제 |

### 수정난이도 (1~5) - 고치는 데 드는 비용과 위험

| 점수 | 기준 |
|:---:|---|
| 5 | 변경 범위가 넓고, **동작 보존이 까다로운 분기**가 많다. 여러 단계로 나눠야 한다 |
| 4 | 여러 파일·계층에 파급. DB·API 보존 장치(Converter 등)가 필요하다 |
| 3 | 한 도메인 안의 구조 변경. 미묘한 차이를 놓치면 동작이 바뀐다 |
| 2 | 기계적 변경이 대부분. 파급이 작다 |
| 1 | IDE 리팩토링 기능(이름 바꾸기 등)으로 끝난다 |

### 점수 → 심각도

| 점수 (영향 × 난이도) | 심각도 | 의미 |
|:---:|:---:|---|
| 20~25 | ★★★★★ | 가장 비싼 부채. 테스트로 완전히 고정한 뒤 **작은 단계로 쪼개서** 진행 |
| 15~19 | ★★★★☆ | 핵심 리팩토링. 별도 작업 단위로 계획 |
| 10~14 | ★★★☆☆ | 상위 작업과 묶어서 처리 |
| 5~9 | ★★☆☆☆ | 짧은 작업. 기회가 될 때 처리 |
| 1~4 | ★☆☆☆☆ | 다른 작업 중에 함께 정리 |

## 3. 영향도 × 난이도 매트릭스

```
            난이도 낮음 (1~2)                 난이도 높음 (3~5)
          ┌────────────────────────────┬────────────────────────────┐
 영향 높음 │  ① 빠른 성과 (Quick Win)    │  ② 핵심 부채 (계획 필요)    │
  (4~5)   │     S04 강결합              │     S02 God Class   ★★★★★  │
          │                            │     S03 매직넘버    ★★★★☆  │
          │                            │     S01 테스트 부재 ★★★★☆  │
          │                            │     S05 중복 · S07 DTO     │
          ├────────────────────────────┼────────────────────────────┤
 영향 낮음 │  ③ 함께 정리 (Fill-in)      │  ④ 신중히 (가성비 확인)     │
  (1~3)   │     S08 S09 S10 S11         │     S06 빈약한 도메인       │
          │     S13 S14 S15 S16         │                            │
          └────────────────────────────┴────────────────────────────┘
          ⚪ S12 조용한 실패 - 매트릭스 밖 (리팩토링 대상 아님, 재설계 단계)
```

| 구역 | 전략 |
|---|---|
| ① 빠른 성과 | **먼저 한다.** 작은 비용으로 다음 작업(테스트)을 쉽게 만든다 - S04 를 고치면 S01 테스트에서 메일·로그를 가짜로 검증할 수 있다 |
| ② 핵심 부채 | **테스트로 고정한 뒤 작은 단계로.** 한 번에 하나의 기법만 적용하고 단계마다 green 을 확인한다 |
| ③ 함께 정리 | 별도 작업으로 잡지 않는다. ①②를 하면서 지나가는 길에 정리한다 (보이스카우트 규칙) |
| ④ 신중히 | 영향 대비 비용이 크다. S06 은 ②의 S02·S05 를 진행하며 **필요한 행위만** 엔티티로 옮기는 식으로 점진 적용한다 |

## 4. 06 과의 관계 - 같은 스멜, 다른 질문

| 문서 | 축 | 답하는 질문 | 결과 |
|---|---|---|---|
| [06-심각도-표.md](06-심각도-표.md) | 영향 × **범위** | 무엇이 가장 넓게 아픈가 → **처리 순서** | 치명 4건: S01 · S02 · S03 · S04 |
| **07 (이 문서)** | 영향 × **수정난이도** | 무엇이 가장 비싸고 위험한가 → **작업 계획·공수** | ★5: S02 · ★4: S03 · S01 / 빠른 성과: S04 |

두 관점을 합친 결론:

1. **S01 특성화 테스트**를 가장 먼저 쓴다 (06 의 전제 조건).
2. 이어서 **S04** 를 처리한다. 06 에서는 치명, 07 에서는 ★2(쉬움)라 **효과 대비 비용이 가장 좋다.** 끝나면 메일·로그 검증을 가짜 구현으로 바꿀 수 있다.
3. **S03 → S02** 는 ★4~5 의 큰 작업이다. 각각 여러 커밋으로 나누고, 커밋마다 특성화 테스트 green 을 확인한다.
4. ★1 스멜은 계획에 따로 넣지 않고 위 작업 중에 함께 정리한다.

> **보존 대상:** 어떤 점수의 스멜을 고치든 API · public 시그니처 · DB 정수값 · 조용한 무시 동작 · 메일/로그 문구는 바꾸지 않는다. 특성화 테스트 본문은 수정하지 않는다.
